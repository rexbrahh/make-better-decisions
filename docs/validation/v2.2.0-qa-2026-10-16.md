# v2.2.0 QA record

Date: 2026-10-16.
Baseline: v2.1.6, signed release commit `03ea1d6ca725b273951820a04063a0b7115b2aaa`.
The owner selected the [separate Snap client design](../superpowers/specs/2026-10-15-subq-provider-design.md).
Normal host policy retains Jev during qualification.

## Confirmed boundaries and repairs

| Issue | Repair | Evidence |
| --- | --- | --- |
| A 17-question Snap request returned HTTP 422 | Send deterministic batches of at most 16 | Initial wire probe, batch tests and live 33-question control |
| Long-input requests exceeded the Jev deadline | Share one ten-second Snap deadline and four-request limit across fragments | Four-batch wire probe, deadline and concurrency tests |
| Existing receipts did not distinguish providers | Match provider, model, context profile and review contract | Cross-provider cache, local receipt and native-shaped inheritance tests |
| Evidence helpers fixed the smaller Jev budget | Pass the selected profile through every build and final trim | Larger source, full-file hash, Unicode, omission and redaction tests |
| Invalid signed provider policy could use availability mode | Validate the selection before transcript loading and treat invalid selection as a configuration error | Both host regressions cover readable and missing transcripts, deny reviewed tools and retain ordinary reads |
| Credentials in identifiers could bypass value redaction | Reject credential-bearing request identifiers and redact stored identifiers | Request, collision and remote-metric key-rotation regressions |
| A failed edit fragment left sibling requests running | Cancel the shared operation and retain the first cause | Concurrent failure regression |
| An explicit valid selection could not repair an invalid prior selection | Replace only the selected provider before plan validation | Both-host installer regression, with prior signed state unchanged during preview |

The final four cases were reproduced before their repairs.
Two independent source reviewers identified the availability, metric and cancellation cases.
The request-identifier and explicit-recovery checks extended those confirmed boundaries.
Provider selection comes only from signed installation policy. Tool payload and environment selectors cannot change it.

## Live measurements

The initial typed API probe accepted yes/no, choice and score questions.
Production gates use yes/no and choice. This release does not add score support.
The live API accepted 255 choice criteria and rejected 17 questions in one request.

Long-input retrieval controls passed at 34,910 and 139,258 input tokens per request.
The 33-question integration control completed three batches in 3.298 seconds.
Its reported 391,815 input tokens are the total across three requests, approximately 130,605 per request.
This does not qualify a single 384K-token input.

Six labeled live gate cases passed: supported UTF-8 advice, missing-platform evidence request, omitted SQLite requirement refusal,
routine verification, an exact edit and denial of an unreviewed material edit.
Observed elapsed times ranged from 244 to 456 milliseconds for these small cases.
These are fixed controls, not a reliability or calibration study.

## Remaining qualification

Default promotion requires a larger fixed, labeled comparison corpus with reliability, false-release, false-block, latency and cost results.
Provider agreement is not ground truth. The current six cases cannot establish these rates.
Native GUI operation, new live worker inheritance and the full advertised Snap context window remain unverified.
The benchmark peer's `evals/` and `docs/evaluation/` work is outside this release.
